# 4. 画质与色彩

## 4.3 HDR 色彩处理应该从手动参数升级到元数据驱动

### 4.3.1 现状：五个环境变量在冒充码流

`grep -n 'colorimetry|colorspace|quantization|xfer_func|mastering|CLL|SEI|vui' v4l2hevc.c`
→ 零命中。整条链**没有接收色彩元数据的入口**，SPS 解析器只读到
`chroma_format_idc / 宽高 / conformance window / bit_depth / poc`（`sps_try`，:828），
VUI 那一截被整个跳过，SEI 一个字节都没解。

于是原本由码流携带的每个量，都被 `tm_build()`（v4l2hevc.c:1209）固定成常量：

| 参数 | 码流里的真值在哪 | 现在实际用的 | 后果 |
|---|---|---|---|
| 传递函数 | VUI `transfer_characteristics`（PQ=16 / HLG=18 / 709=1） | 只要 `HDR=1` 就假定 PQ | HLG、BT.709 全范围片被当成 PQ 映射，画面发灰 |
| 原色/色域 | VUI `colour_primaries` | 恒按 BT.2020 | SDR 709 片被套 2020 系数，肤色过饱和 |
| 矩阵系数 | VUI `matrix_coeffs` | `HC_K2020_*` 一组 | 709 内容错色（`HC_K709_*` 已经写在头文件里但没人选） |
| 全/有限范围 | VUI `video_full_range_flag` | `TM_FULL` 存在才算 | 默认按 16..235 处理，全范围源暗部压缩 |
| 内容峰值 | SEI `maxCLL`，缺省 `max_display_mastering_luminance` | `TM_SRC_PEAK=1000` | **实测零影响**，见下 |
| 主监视器 | SEI mastering display（ST 2086） | 完全没解 | 无法知道 1000 还是 4000 nits 母版 |

两条自我检查把这件事钉死了：

1. `hdr-selftest.c` 的 `t_srcpeak()` 打印：`src_peak=1000 vs 4000：Y 差 0 码、gain 差 0 条`。
   即 `hc_curve()` 里 `x = L / c->target` 根本不看 `src_peak`，它只在 `tm_build()`
   里被 `if (tm.src_peak < tm.target)` 夹一次下限。**手动参数里最能体现"内容"的那一个，
   实际上什么也没做。**
2. 同一个量在两处有不同默认值：`v4l2hevc.c:1218` 的 `TM_SAT` 是 0.85，
   `glout.c:178` 是 0.90。`hdrcolor.inc` 头注释已经把这笔账记下来了，
   而只要参数还停在环境变量里，这种漂移就会继续长。

所以"手动参数"的问题不是缺一个更好的默认值，而是：**我们手里有真值，却用手拧的估计值去替代它**。

### 4.3.2 元数据从哪来：两条路，选 (b)

**(a) 扩 ffprobe 一次探测** —— 壳里已经这么干过（判 HDR 用），补 `color_transfer`、
`color_primaries`、`color_space`、`color_range`、`side_data` 里的 mastering/CLL 即可，
半小时收工。缺陷是粒度：整片一个值，SDR/HDR 混剪、片头广告接正片、多段拼接的片子必然错。

**(b) 在 demux 里解 VUI + prefix SEI** —— 每帧准确，且和 §1 那条流式 AU 切分共用同一个
NAL 遍历循环（`sps_size()` 已经在扫 NAL 头找 32/33，多认两个类型就走完了）。

选 (b)。理由不是"更正确"，而是**它不增加新模块**：AU 切分无论如何都要走每个 NAL，
VUI 在 SPS 里、mastering/CLL 在 prefix SEI(39) 里，都是顺手取。
(a) 保留为兜底：`ffprobe` 的值只在码流里完全没元数据时用作"猜"，且必须打印来源标签。

这条依赖是硬的：如果 §1.2 最终决定"不动流式切分、只用 mpv 钟"，那就没有 (b) 的落点，
本节的实现方式降级为 (a)，粒度缺陷得接受。

### 4.3.3 元数据模型：一个结构，三个来源标签

```c
enum color_src { CS_UNKNOWN, CS_DEFAULT, CS_CONTAINER, CS_BITSTREAM };

struct color_desc {
	enum color_src src;
	int primaries;      /* 1=BT.709  9=BT.2020 */
	int transfer;       /* 1=BT.709  16=PQ  18=HLG */
	int matrix;         /* 1=BT.709  9=BT.2020 NCL */
	int full_range;     /* VUI video_full_range_flag */
	double md_max;      /* mastering_display_max_luminance nits（0=未知） */
	double md_min;
	double max_cll;     /* maxCLL nits（0=未知） */
	double max_fall;
};
```

三个来源按优先级覆盖，**逐字段**而不是整块替换（SEI 只带亮度、VUI 只带色彩空间，
真实码流里常见一个有一个没有）：

1. `CS_BITSTREAM`：VUI + SEI。有就用，来源标记打出来。
2. `CS_CONTAINER`：mkv `colr`/`mdcv`/`clli` atom（走 (a) 时是 ffprobe）。
3. `CS_DEFAULT`：今天的常量，且必须打印 `COLOR: 无元数据，回退默认`——
   静默回退是这次改造最容易被后来的自己骗过去的地方。

### 4.3.4 元数据 → 参数的映射规则（哪些让位、哪些不让）

关键区分：**元数据描述内容，不描述这块屏**。所以不是所有旋钮都交给码流。

| 目标参数 | 来源 | 说明 |
|---|---|---|
| `on` | 元数据：`transfer==16` | PQ 才开映射；HLG/709 一律不套 PQ 曲线 |
| `src_peak` | `max_cll` → 无则 `md_max` → 无则常量 | 这才让 `src_peak` 第一次真正参与运算 |
| `sat` | 由 `primaries` 派生（`hc_sat_from_primaries()`） | 2020→709 才压；709 源 `sat=1.0`（不动作），不再当独立旋钮；P3 按面积比的对数插值；未标按 2020 兜底并打日志 |
| `full` | VUI `full_range` | `TM_FULL` 降级为覆盖项 |
| 矩阵系数 | VUI `matrix` | `HC_K709_*` / `HC_K2020_*` 二选一，不再写死 |
| `target` | **面板，不是码流** | SDR 参考白仍由 `TM_TARGET`（X96Max 实测 200nits 量级）给 |
| `curve` / `knee` | **策略，不是码流** | 拐点和曲线形状是口味/防 banding 的手段，元数据里没有对应物 |
| `gain_mode` | 策略 | `lin` 仍是默认方向 |

一句话：**亮度上限、色域、范围、矩阵交出去；曲线形状、参考白、增益算法留在手里。**

> **实测（hdr-selftest [6]/[10]，sat=0.85 / target=200 / knee=0.7）**——已落地两条、还剩一条：
> 1. ~~`g *= sat` 是无条件乘，所以"膝点以下 g=1（不动作）"实际是 0.85。~~
>    **已改**为 `g = 1 + sat*(g-1)`（sat 只缩放增益的作用量，不动恒等段）：
>    sat=1 全量、sat=0 恒等 1、膝点以下恒为 1.0。实测 709 蓝 1000nit
>    lin 68.9 → **58.0**，正好回到"不碰色度"的基线。
> 2. ~~`sat` 没按 `primaries` 派生，是常量默认值（0.85/0.90），
>    和上面"不再当独立旋钮"冲突。~~
>    **已落地**：`hc_sat_from_primaries(primaries, wide)` 放进 `hdrcolor.inc`，
>    软映射与 GL 同一条规则（wide 各保留 0.85/0.90）：709→1.0、2020→wide、
>    P3-D65→0.95（u'v' 面积比 1.25 与 1.90 的对数插值）、未标→wide。
>    `TM_SAT` 降级为覆盖项（日志标 `env`）；VUI 后到时 `tm_refresh()`/
>    `tm_peak_sync()` 按新 `primaries` 重算 sat 并重建表，不再拿 709 的 1.0 压 2020 片。
>    hdr-selftest [10] 覆盖：709 不动作、膝点(v<136)以下增益恒 1024、sat 只缩放
>    “偏离 1 的量”（增益[235] sat=1.00 → 20，sat=0.85 → 171）。
> 3. ~~软映射路径没有 2020→709 矩阵，只有标量色度增益：色域外原色
>    （2020 红/绿/青）对参考最坏差到 127.6 码。~~
>    **已落地**：`hc_chroma709()` 进 `hdrcolor.inc`，矩阵改成入参
>    （`hc_mat(primaries)`），`hc_needs_mat(primaries)` 决定要不要走：
>    2020/未标 → 2020 主矩阵，P3-D65 → P3 主矩阵（§4.3.4.1），709 恒等。
>    GL 侧一度是手抄的九个常数（"共用一份"只是数值相同，源码里两份），现在
>    改成 `uniform mat3 uGm`，由 `gm_upload()` 从同一份 `hc_mat()` 上屏。
>    顺序是「色度 → Y」，因为 `gain[]/lut[]` 都按**输入码**编表（原来色度在 Y 之后跑，
>    拿输出码查输入表）；编回 709 时以 LUT 的 Y 为基准，矩阵不挪亮度。
>    实测（hdr-selftest [11]，码差对线性域参考）：
>    | 色块 | 标量增益 | 矩阵(sat=1) | 矩阵+sat0.85 |
>    |---|---|---|---|
>    | 2020 红 | 75.2 | 41.9 | 46.1 |
>    | 2020 绿 | 126.2 | 113.4 | 122.8 |
>    | 2020 蓝 | 71.2 | 63.6 | 74.4 |
>    | 2020 青 | 127.6 | 54.7 | 74.1 |
>    | 肤色 | 6.4 | 8.3 | 6.1 |
>    | 最坏 | 127.6 | **113.4** | 122.8 |
>    绿还剩 113 码：矩阵 + 去饱和都压不回 709 三角形的绿，参考本身是
>    "夹到 0 之后的逐通道曲线"，GL 路径同样 113 —— 这是色域外无法互转的部分，
>    不是实现的锅。增益算法（lin vs code）的结论仍然只在色域内 + 暗部低饱和区成立：
>    `g = 1 + sat*(g-1)` 之后 lin 9.6 码（= 不动作基线）、code 16.4 码。

#### 4.3.4.1 P3-D65 的主矩阵（补上"暂留标量增益"那一档）

Display P3 只比 709 宽一点点，和 2020 是同一类问题，系数却不同：白点都是 D65，
所以矩阵行和恰好为 1（灰一个码都不动），只有原色差。同一套流程（原色 x/y + 白点
→ 线性主矩阵）算出来：

```
 1.2249 -0.2249  0.0000
-0.0421  1.0421  0.0000
-0.0196 -0.0786  1.0983
```

三点记下来：

1. **和 2020 那组同源**：`HC_M_*` 那九个"BT.2087 派生系数"其实就是线性光
   2020→709 的主矩阵（逐位相同，`hdrcolor.inc` 的注释写清了），所以 P3 也用
   线性主矩阵；输入编码仍是 2020 NCL（`matrix_coeffs=9`，P3 片的事实标准），
   primaries 和 matrix_coeffs 本来就是两件事。
2. **判据不能看"钳位后的码差"**：色域外原色两条路都会撞 16/235，谁推得狠谁
   "看起来"更准（P3 红：P3 系数 52.7 vs 误用 2020 的 41.9 —— 2020 系数把 G/B
   推成负数撞到 16，正好和参考撞在一起）。所以 hdr-selftest [12] 另外用
   **709 色域内**的点、比非线性 RGB、不带曲线不带钳位：P3 系数 均 8.3 / 峰 47.4
   码，误用 2020 系数 均 24.0 / 峰 86.2，恒等 均 16.7。
3. **这只是"码值域乘线性矩阵"这一档里最好的选择**：全色域随机取样时，码值域
   最小二乘最优是 `1.2604 -0.2576 …`（2020 是 `1.7094 -0.6308 …`），和线性
   主矩阵有差别，能再压一点均值；但它会改掉已上线的 2020 观感，和"码值域只做
   一次近似、Y 由 LUT 定死"的架构也冲突，先记录不动。

另外 §4.1.3 的顺序约束在这里表现为：先有元数据入口，再谈 LUT——LUT 只是这张表的函数。

### 4.3.5 什么时候重建：只有字段变化才重建，且不许当帧生效

- VUI 在 SPS 里。SPS 变化意味着解码参数变化，本来就走 `g_reinit`（§1.10）重建会话 ——
  色彩参数跟着一起重建，天然同步，不需要新机制。
- SEI 可以不换 SPS 就换（分段片、无缝拼接）。这种情况**只重建 LUT，不碰 V4L2 会话**。
- 触发条件用字段比较：`memcmp` 四个整数 + 三个 double 不等才重建，不做"每帧重建免得漏"。
- 重建必须双缓冲：`tm_apply()` 的 NEON 路径把 `tm.lut` 的 16 字节块一次性读进 8 个
  `uint8x16_t`（v4l2hevc.c:1300 起），就地改表会让同一帧的 Y 用旧表、Cb/Cr 用新表，
  肤色直接跳一下。做法：`lut_a/lut_b` 加一个 `cur` 索引，重建写另一份，下一帧开头切换。
- GL 侧注意成本不对称：`build_lut()`（glout.c:174）除了 `hc_build` 还要跑
  `fit_poly()` 拟合并打印误差。重建频率是"每段一次"时无所谓；若发现某些片子 SEI 逐帧抖，
  退化成"字段变化超过阈值才重建"，否则拟合也会跟着抖。

### 4.3.6 交叉校验：两个真值打架时听谁的

V4L2 capture format 里本来就有 `colorspace / xfer_func / ycbcr_enc / quantization`
四个字段（`g_fmt_cap()`，v4l2hevc.c:389 现在只打印宽高，没读它们）。
stateful vdec 驱动不一定填真值，可能只有默认值。

规则：**信我们自己从码流解的 VUI**，驱动字段只用来报警——
两者不一致时打印一行 `COLOR: VUI=bt2020/pq vs V4L2=bt709/srgb（用 VUI）`。
理由：VUI 是原始语法，驱动字段经过一次翻译且未在 meson 上验证过。
（这一条要先实测：`g_fmt_cap` 把四个字段打出来，看 meson vdec 到底填不填。）

### 4.3.7 明确不做

- **不做 HDR 直通**：DPU 没有色彩管理（§4.1 第 1 条），送 PQ 码值进 plane 只会更灰。
  元数据只影响"怎么映射到 SDR"，不影响"是否映射"。
- **不做 HLG**：HLG 是另一条 OETF（场景光 vs 显示光），需要不同的曲线族。
  本期只做**识别**：`transfer==18` 打印一行并回退 SDR 直显，不假装能映射。
- **不追逐帧动态元数据**（HDR10+ / Dolby Vision RPU）：本机的解码与显示链路都不具备，
  解出来也没有第二个消费者。识别到就回退，不实现。
- **不删手动参数**：`TM_*` 全部保留为覆盖项，优先级最高。元数据是默认值提供者，
  不是把现场调试手段收走。

### 4.3.9 实测记录：这一轮抓到的三个真问题

1. **SEI 解析范围错到离谱（已修）**。`stream_next_au()` 把 `sc - s_au_sei` 传给
   `csig_sei()`，也就是"从 SEI 到 AU 结束"——把后面的 VCL 数据也当 SEI 扫。
   而 `s_au_sei` 又是在 `if (!s_au_open)` 的 reset **之前**赋值的，被 reset 清零、
   或者拿到的是下一个 AU 的偏移，`sc - s_au_sei` 变成巨大的 `size_t`。
   症状：`母版=280149 nits`、`maxCLL=26534`，而且**每帧都变**（因为扫的是压缩数据，
   随机命中 payload type 137/144）。修法：改成"每遇到下一个起始码就解析上一个 SEI NAL"，
   范围正好一个 NAL；`csig_sei()` 再加 `n > 1MB 直接返回`兜底。

2. **一个 AU 里可以有多个 SEI NAL（已修）**。x265 就是 SEI 144 一个 NAL、SEI 137 一个 NAL。
   原来 `if (t == 39 && !s_au_sei)` 只记第一个，母版亮度（137）永远读不到，`母版=0/0`。
   修法：每个 type 39 NAL 都解析。

3. **`L()` 的单位是 1/10000 nits，不是 nits**。`master-display=…L(4000,50)` 在规范里是
   0.4/0.005 nits；要 4000 nits 得写 `L(40000000,500000)`。ffprobe 打印的
   `max_luminance=4000/10000` 正是这个意思。解析公式（×0.0001）本来就是对的，
   错的是样本参数——记在这里免得下次又去查代码。

其他两条观察：

- **meson vdec 的 capture format 四个色彩字段全是 default**：
  `G_FMT CAP : 1920x1080 cs=default xf=default enc=default q=default`。
  即 §4.3.6 的交叉校验在这块板子上**永远不会报警**——驱动不填。
  函数留着（其它 SoC 会填），但别指望它当验证手段。
- `COLOR:` 行只在内容信号变化时打印（memcmp 四个 int + 三个 double + V4L2 四字段），
  单片段全片一条，不会刷屏。

### 4.3.10 输出编码：bt709 OETF 是错的，该用 BT.1886（已修，TM_ENC=709 可回退）

HDR 路径一直是「PQ 码 → 线性光 → 曲线压到 0..1 → **bt709 OETF** → 有限范围码」。
最后那一步是错的：SDR 显示器吃的是 BT.1886（纯 2.4 幂）这条 EOTF，要让屏上看到的
线性光是 d，就得按 d^(1/2.4) 编回去。bt709 OETF 在暗部走 4.5 倍斜率的直线段，
比 1886 陡得多，于是整块暗场被压死。

实测（1000nit PQ 灰阶 ramp，盒子 GLDUM 抓帧 vs `ffmpeg zscale npl=1000:t=bt1886`）：

| 内容亮度 | 参考 | 709 OETF（旧） | 1886（新） |
|---|---|---|---|
| 1 nit | 14 | 1 | 14 |
| 2 nit | 19 | 2 | 19 |
| 5 nit | 28 | 6 | 28 |
| 203 nit | 130 | 111 | 130 |
| 1000 nit | 255 | 255 | 255 |

整体 MAE 11.7 码 → 1.5 码；真实 HDR 片里 22~43% 的像素落到纯黑，就是这一步造成的。
中段（≥300nit）两条编码几乎重合，所以只看亮场/彩条永远发现不了。

判据链（这一轮顺带钉死的 range 语义）：

- 盒子的 GL 输出是**全范围 RGB**：SDR 8bit 透传实测 `16→0、226→245`，即
  `(in-16)*255/219`，MAE 0.24 码 —— 这不是 range bug，是正确行为。
- 盒子端到端（`GLDUM` 抓帧 vs 主机按 PQ→BT.1886 独立算的参考，1000nit ramp、
  TM=1 target=1000）：默认 1886 → **MAE 0.39 码**（≈dither 底噪，`x=960 ref 99 / 实测 99`，
  `x=1200 ref 165 / 实测 166`）；`TM_ENC=709` → 12.54 码。着色器里没有第二处 range 误差，
  问题只可能在 LUT 的编码步。
- `hc_build()` 里 `code = 16 + 219*hc_out_oetf(c, d)`，`hc_out_oetf` 按 `c->enc`
  选 1886 / 709；`TM_ENC=709` 回退历史行为，日志里 `enc=bt1886|bt709` 可查。
- 参考真值必须同域：`hdr-selftest` 的参考管线改成 `hc_out_oetf()`，但 [12] 段
  （P3 矩阵 vs 标量增益的码差）阈值是按 709 域标定的，那里固定 `enc=HC_ENC_709`，
  否则码差不可比（换编码只是把同一线性光重新分布到码值上）。
