# 硬解卡死复盘：2026-11-17 04:02:25（播放 39 分钟后）

x96 = 4K VP9/HEVC 硬解 + mpv 播放链路，3840x1600 @24fps，第 56628 帧卡死。

## 结论

1. **不是供料饿死**：卡死瞬间 vififo 只有 421 字节（已弹空），esparser 上游一路跟得上；重建后 vififo 反而堆到 700KB 说明用户态在猛灌，硬件不取。
2. **不是 DPB/buffer 管理问题**：q 从 3 涨到 17 表示驱动侧仍在正常排队；重建把 buffer 全换新（seq 归 0、q=8）后仍是 0 帧完成。
3. **不是中断全灭**：重建后 irq 仍以 +0/+1 递增（st=1），说明只有少数非"帧完成"中断在来，`IrqOnDecodeDone` 类完成中断彻底不来了。
4. wptr 在 start..end 环内继续前进、streamctl=1eb14009 使能位正常、status=00000005 与健康期一致 → **寄存器层面看不出错误，是 VDEC 硬件/固件在某一帧进入 hang（不再上报完成），驱动无能为力**。

即：卡死点在 VDEC 固件内部（单帧处 hang），streamoff/streamon 级别的软复位救不回来。要恢复只能做上层的全块复位（时钟/电源 gate 复位或模块 reload）。

## 硬复位（AO 真掉电再上电）—— 2026-11-17 落地

需求：卡死后 close+open（streamoff/streamon）救不回来，`vdec_poweroff()` 只关时钟，
硬件/固件状态原样保留。要真正复位必须翻 AO 的 `GEN_PWR_SLEEP0/ISO0`。

用法（无活动会话时）：
```sh
sh /root/vdec-reset.sh          # = echo 1 > /sys/module/meson_vdec/parameters/hard_reset
```
模块：`/root/vdec-hr5.ko`（源码 meson-vdec/vdec.c，`vdec_hr_run()`）。
流程：dos/dos_parser/vdec_hevc 时钟 → 上电 + `DOS_SW_RESET3`/`GCLK_EN3`/`MEM_PD_HEVC`/ISO 清 →
隔离 + `MEM_PD_HEVC=0xffffffff` + `SLEEP0` 掉电 → 再上电。搞完留在「刚上电、未装固件」的干净状态。

### 踩的坑（很重要）
1. **无会话时写 `HEVC_ASSIST_MBOX1_MASK` / `HEVC_MPSR` 会把 AXI 锁死**：整机当场硬挂，
   无 oops、无 pstore、netconsole 也不出字，只能靠硬看门狗拉回来（实测两次，每次 ~14s 后自动重启）。
   所以硬复位里**绝不能**去「停固件」，掉电已经清干净，MPSR 交给下个会话的 `__vdec_hevc_start`。
2. 挂死无日志时不要指望 printk：console 会走延迟刷写，CPU 卡在 MMIO 里那些行全丢。
   定位靠 `hard_reset` 参数的分步模式（2..6）二分：每步单独 echo 一次，看机器活不活。
3. 反过来，先上电再写 DOS 寄存器是对的：上一会话已把整块掉电+隔离，直接写会挂。

验证：硬复位后 `playtest.sh` 4K 3840x1600 → 496/496、376/376、304/304 AUs，resets=0，21~23.9fps。

## 卡死自愈落地：把硬复位接进 stop 路径 —— 2026-11-18

上一节证明了两件事：卡死点在 VDEC 固件内部；`streamoff/streamon` 救不回来，
只有 AO 全块掉电+上电（`hard_reset`）能清。而用户态的自愈手段恰好只有
`streamoff/streamon`，所以 39 分钟后那次卡死必然「5/5 自愈失败 → 退出」。

修法：**别指望用户态能复位硬件，把 `vdec_hr_run()` 挂到驱动自己的会话销毁路径上。**

### 改了什么（`vdec.c` / `vdec.h` / `vdec_helpers.c`）

| 位置 | 改动 |
|---|---|
| `vdec_helpers.c: dst_buf_done()` | 每次帧完成打 `sess->last_frame_jiffies`：卡帧时 IRQ 还在零星进来，只有「帧完成」是可靠活性信号 |
| `vdec.c: vdec_check_stall()` | 定时 work 里判：`status=RUNNING` 且帧龄 ≥ `hr_stall_ms` 且 `pend>0` → 标 `sess->stalled`，打一次 `dbg_dump` 现场 + `STALL:` 告警 |
| `vdec.c: vdec_poweroff()` | 停之前再判一次（用户态可能比 work 先 streamoff），`vdec_ops->stop()` 之后补一次 `vdec_hr_run(core, 6)` |
| `vdec.c` | 新参数 `hr_mode` / `hr_stall_ms` / `hr_count` |
| `vdec.c: vdec_dbg_work()` | `dbg_ms=0` 时也以 `hr_stall_ms` 为周期跑（只做卡死检测，不刷日志） |

参数：

```
hr_mode=0    从不复位（老行为）
hr_mode=1    只在检测到卡帧时复位
hr_mode=2    每次 stop 都复位（默认）
hr_stall_ms  多久没有帧完成算卡死（默认 500ms ≈ 24fps 的 12 帧）
hr_count     已做过的硬复位次数（只读，统计/验证用）
```

### 为什么默认 `hr_mode=2`

- 判卡死有时间窗，`hr_mode=1` 会漏判（用户恰好在卡死后、超时前暂停等）；
- 正常 stop 也复位还顺带好处：硬件永远从「probe 完的干净状态」进下一会话；
- 代价实测 ~17ms（`power-cycling` 到 `hard reset n=6` 两条 printk 的间隔），
  一次 streamoff 只付一次。

### 时序（卡死 → 自愈）

```
固件卡在第 N 帧
  ├─ 500ms 后 vdec_dbg_work: STALL: no frame done for 5xx ms + dbg_dump 现场
  ├─ 播放器 12s 无新帧 → streamoff（进驱动的 vdec_poweroff）
  │    ├─ vdec_ops->stop()：隔离 + 关存储 + 掉电（固件状态还在，老版本就死在这）
  │    └─ vdec_hr_run(6)：AO SLEEP0/ISO0 掉电 → 上电 → DOS 复位，硬件归零
  └─ 播放器 streamon（新会话）：装固件 → 出帧，播放继续
```

### 验证（2026-11-18 23:12~23:35，盒子在跑 7.2.12-x96-trim）

1. **不炸（最担心的 AXI 锁死）**：`hr_mode=2` 下连做 3 次「解码 → 关闭」，
   每次都走完整 AO 掉电+上电，盒子没挂，每次 reset 17ms：

```
power-cycling VDEC_HEVC on stop (mode=2 stalled=0 age=190ms pending=0)
hard reset n=6 ret=0 gclk=ffffffff mempd=00000000
```

   三次 1080p8 编码解码均 191/192 帧、`decode-only=93 fps`，与改动前一致 → 无回归。
2. **下一会话装固件正常**：紧跟在硬复位后面的会话照常出帧（run 2 / run 3 都正常），
   说明「掉电→上电→留空」的状态确实能被 `__vdec_hevc_start` 重新拉起。
3. **坏码流不会顺手把机器打死**：把码流中段 4000 字节随机覆盖，固件走
   `Unrecognized dec_status` 的软中止路径（老行为），stop 时照样复位。
4. **长跑（4K 3840x1600 合成码流，单会话不 streamoff）**：
   12.5 分钟 / 72124 帧（约 87fps）无 STALL、无复位 → 合成码流复现不出这个固件卡死，
   卡死更像「特定码流内容」触发，而不是纯时长/帧数。

### 现场怎么看

```sh
# 卡死瞬间（驱动自己就打，不需要提前开 dbg_ms）
dmesg | grep -a "STALL: no frame done"      # 一行 + 后面紧跟一条完整 VDECDBG

```

`hr_mode` / `hr_stall_ms` 可运行时改（0644），调门限不用重载模块：

```sh
echo 1 > /sys/module/meson_vdec/parameters/hr_mode   # 退回「只在卡死时复位」
```
